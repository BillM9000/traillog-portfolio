# TrailLog Testing Methodology

> **Suite Count:** 17 | **Total Tests:** 168 | **Framework:** Playwright | **Last Updated:** 2026-03-30

## Overview

TrailLog uses Playwright browser automation for end-to-end integration testing against the production database. Tests exercise the full request lifecycle — HTTP request through Express middleware, database operations, and JSON response validation — using the same authentication and CSRF mechanisms as real users.

## Test Personas

Tests use 10 pre-configured user accounts with saved authentication state, covering every role and permission level in the system:

| Persona | Role | Purpose |
|---------|------|---------|
| `sysadmin` | Global admin, troop admin | Admin operations, platform settings, adventure management |
| `troopcreator` | Troop admin (no adventures) | Troop-only admin operations, settings management |
| `troopjoiner` | Regular member | Join flows, member-level access |
| `adultleader` | Adult member | Member self-service, date/skill updates |
| `parenttrek` | Parent (trekking) | Parent-scout linking, trekking participation |
| `parentsupport` | Parent (support crew) | Support crew role, parent dashboard |
| `scout-alpha` | Scout | Scout restrictions, limited permissions |
| `scout-bravo` | Scout | Second scout for interaction tests |
| `invited` | Invited user | Invitation acceptance flow |
| `codejoiner` | Join-by-code user | Invite code flow, auto-approval |

Authentication state files are generated by a global setup script that logs in each persona once and saves cookies/session state for reuse across all test suites.

## CSRF Handling

All mutating requests (POST, PUT, DELETE, PATCH) require a valid CSRF token. Tests extract the `XSRF-TOKEN` cookie from the browser context and pass it as an `X-CSRF-Token` header:

```javascript
async function getCSRFToken(context) {
  const cookies = await context.cookies();
  const xsrf = cookies.find(c => c.name === 'XSRF-TOKEN');
  return xsrf?.value || '';
}
```

This mirrors the double-submit cookie pattern used in production.

## Test Architecture

### Helper Functions

Each suite includes reusable helpers that handle the data model's permission hierarchy:

- **`findTestTroop(page)`** — Iterates the authenticated user's troops and identifies one where they have admin access (by probing the invite-code endpoint).
- **`findAdventure(page, troopId)`** — Locates an adventure within a troop and ensures the current user is a member. For global admins, this includes a self-add step since `requireAdventureMember` middleware does not bypass for system admins (only `requireAdventureAdmin` does).
- **`getCSRFToken(context)`** — Extracts the CSRF token from cookies for mutating requests.

### Suite Details

**Suite 15 — Email Notifications** covers every API endpoint that triggers an email: signup verification, password reset, join request notification, member approval/denial, invitation sending, training scheduling, token-based approval, and link requests. Tests verify the endpoint returns success and the correct response structure without requiring actual email delivery.

**Suite 16 — Member Lifecycle** tests the complete user journey: account creation, unverified login blocked, join-by-code with auto-approval, admin member management (add, remove, role changes), member self-service (dates, skills), scout restrictions (cannot create troops, limited API access), non-admin restrictions, and troop departure validation.

**Suite 17 — Data Mutations** validates all write operations: member data updates (dates, skills, gear, medical, admin tasks), manual member CRUD with cascade verification, training event lifecycle (create, list, delete, RSVP), troop settings (duplicate detection, invite code regeneration), adventure skills CRUD, gear mutations (catalog access, status persistence, array validation), ICS calendar export, and data isolation (non-admin cannot add members or delete events).

## Key Design Decisions

### Production Database Testing

Tests run against the actual production database rather than a test fixture. This catches real-world issues like:
- Permission middleware behavior with actual user/troop/adventure relationships
- Data cascade operations across related tables
- Schema constraints and validation rules

**Safety rule:** Tests never mutate critical state (e.g., admin leaving their only troop, deleting real data). Destructive test scenarios use fake IDs or are designed to be idempotent.

### Persona-Based Access Control Verification

Each test uses the minimum-privilege persona required for its operation. This verifies the middleware chain works correctly:
- `sysadmin` for operations requiring global or troop admin access
- `adultleader` for member-level self-service
- `scout-alpha` for verifying scout restrictions
- `codejoiner` for invite code flows

### Middleware Discovery

Testing revealed an important architectural detail: `requireAdventureMember` does NOT allow global admin bypass, while `requireAdventureAdmin` does (and also allows troop admin bypass). This means global admins must be explicitly added to an adventure's member list before they can access member-scoped endpoints.

## Running Tests

```bash
# Full suite (all 17 suites, ~7 minutes)
npx playwright test

# Single suite
npx playwright test tests/email-notifications.spec.mjs

# With headed browser (for debugging)
npx playwright test --headed

# Generate auth state files (run first)
npx playwright test --global-setup=tests/global-setup.mjs
```
